# Hollowwake client runtime changes — 0.3.2

These are original implementation changes, not a completed Fortnite port or an Xbox-installable client. No game executable, Epic assets, unlicensed runner code, project credentials or private signing keys are included. Existing companion, live Sites website/backend, accounts, admin authorization and rollback releases are unchanged in this iteration. The prior exposed Sites bypass was rotated and rejected in the preceding iteration; its evidence remains in the 0.3.1 report.

## Static TLS/thread implementation

`tls/Donor.cpp` implements a bounded process-lifetime TLS donor. The intended mapper loads a separate signed/packaged donor DLL for every guest module using the OS loader, obtains the OS-assigned static TLS index, copies the guest's initialized template and zero-fill into that slot, and writes that index into the relocated guest AddressOfIndex. New OS threads receive per-thread copies via donor DLL thread attach; `InitializeGuestThread` supports an explicit initialization guard for callbacks on already-existing host/thread-pool threads. A module cannot be rebound; the template plus zero-fill is limited to 64 KiB; at most 16 callbacks are accepted. The mapper, rather than BindGuest, must invoke the guest PROCESS_ATTACH callbacks after its entire import/TLS graph is ready. Do not unload a bound donor.

The implementation reads the x64 Windows static TLS vector through GS:[0x58]; it does not replace the host vector or fabricate slot indexes. This is an architecture-specific Windows ABI assumption and remains unverified on Xbox. Desktop LoadLibrary is only used in the original Windows test; a packaged UWP integration must use an appropriately packaged DLL loader. Thread-pool callback interception, cross-module initialization/teardown ordering, loader-lock interactions, preexisting guest threads and fatal thread termination still require runtime-wide integration. This is not a claim of complete Fortnite threading compatibility.

`tests/MappedTls.cpp` is a narrow original-code mapper, not a general game loader. It executes only the build's original no-import/no-unwind TLS fixture. It relocates its image, uses non-writable executable sections, installs the donor index, and executes actual compiler-generated static-TLS instructions on multiple threads. It must never be extended to load arbitrary game images without the missing import, unwind, bounds, dependency and lifecycle machinery. Failed build/run logs are retained rather than treated as successful tests.

## CoreWindow/DXGI implementation

Static inspection of the exact 6.21 main executable found `CreateDXGIFactory`, `CreateDXGIFactory1` and `D3D11CreateDevice` imports; it does not directly import `D3D11CreateDeviceAndSwapChain`. `graphics/GuestImports.cpp` therefore supplies exact-ABI hooks for these three imports. Bind the real CoreWindow once before guest execution. Unknown imports return no hook, not a success placeholder.

`CoreWindowBridge.cpp` implements IDXGIFactory/IDXGIFactory1 COM identity/refcounting, native adapter enumeration and an intercepted CreateSwapChain. It queries the device's real DXGI adapter/factory and calls CreateSwapChainForCoreWindow, returning the actual OS swap-chain COM interfaces. It translates the supported windowed, single-sample desktop descriptor into a flip-sequential CoreWindow descriptor. Exclusive fullscreen, multisampling, unknown flags, software adapters and unsupported formats fail explicitly. The helper for combined D3D11 device/swap-chain creation is retained for dependencies, not mistaken for the main executable's observed path.

This is a narrow bridge, not a full DXGI/windowing emulator: newer factory interfaces, adapter/output GetParent factory escape paths, device-loss/recreation, desktop output/mode semantics, complete swap-chain fullscreen/resize interception and cross-thread CoreWindow access remain unresolved. Native adapters/devices are returned; their parent factories must not be assumed to be intercepted. MakeWindowAssociation records only the fixed CoreWindow policy; it does not create a desktop HWND or install a Win32 message loop.

## Exact remaining package blockers

A self-contained APPX attempting real Fortnite entry is not produced merely by compiling these helpers. The current original mapper deliberately rejects imports/unwind and cannot load this client's 821 normal plus 260 delayed imports, dependency graph or its executable initialization. A complete authorized mapper/compatibility runtime is still missing. The previously reviewed experimental runner has no established standard reuse licence and must not simply be redistributed as a finished runtime.

The real executable also requires desktop window/message behavior (`CreateWindowExW`, `RegisterClassW`, `PeekMessageW`, `DispatchMessageW`, `GetRawInputData`, etc.), dynamic DLL loading, exception/unwind registration and thread/process semantics that these helpers do not implement. CoreWindow swap-chain conversion alone supplies none of those. Controller input must reach the actual engine's input system, not just a host shell.

The existing client621 backend prototype remains disabled and wire compatibility unproven. Native in-process exchange, route/base-URL integration, client OAuth refresh, required 6.21 service/config/profile defaults, XMPP/presence and asset-validated cosmetics still require implementation/validation. Website sign-in is not Fortnite login. Matchmaking remains unavailable; no match service was added. Game files remain private and no permission to redistribute them is presumed.

No original game or third-party launcher is executed in this work. Windows fixture execution and UWP API compilation/linkage must be reported separately from an actual UWP game loader and Xbox execution. No claim of original loading/lobby rendering, controller/locker/shop integration or Xbox success follows from these checks.
